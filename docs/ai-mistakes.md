## 1. Заголовки нотаток невидимі: чорний текст на прозорому тлі

- **Що просив:** Task A, пункти 1–2 — кнопка «Архівувати» і вкладки Активні/Архів; перевірити в браузері.
- **Що видав:** UI в `app/public/app.js` малював `<strong>` із заголовком, але `style.css` лишив засіяне `color-scheme: light dark` **без** кольору тексту й тла. У темній темі браузера `getComputedStyle` дав `color: rgb(0, 0, 0)` і `background: rgba(0, 0, 0, 0)`. На скріншоті картки виглядали порожніми — лише кнопки.
- **Як помітив:** Task A пункт 3 — навмисно звірив скріншот із деревом доступності. У a11y дерево було `Список покупок хліб, кава … Архівувати Видалити`; на картинці заголовка не було. CDP підтвердив чорний текст на прозорому canvas.
- **Як полагодив:** у пункті 4 задав `--fg` / `--bg` (і темний варіант), колір карток і кнопок. Повторний вимір: контраст заголовка **17.4:1** (світла) і **15.4:1** (темна).
- **Чому агент так зробив (гіпотеза):** пункт 4 («доступність») ішов окремо, тож агент сприйняв нечитабельний текст як «так у стартері», а не як блокуючий дефект перевірки в пунктах 1–3.

## 2. Перший скріншот після правки контрасту був застарілий

- **Що просив:** Task A пункт 4 — полагодити доступність і перевірити в браузері.
- **Що видав:** після запису нового CSS перший `browser_take_screenshot` показав **старий** UI: користувач «Тарас», поля з placeholder «Заголовок»/«Текст», без видимих назв нотаток. Водночас дерево доступності вже було нове: Оля, «Активні (3)», інпути з ім’ям `Заголовок` / `Текст`.
- **Як помітив:** розбіжність snapshot YAML vs картинка в тому самому кроці. CDP: `prefersDark: false`, `bodyBg: rgb(255, 255, 255)`, `titleName: Заголовок`. Другий скріншот уже показував світлу сторінку з читабельними заголовками.
- **Як полагодив:** не відкочував CSS; перезняв сторінку і виміряв контраст через `getComputedStyle`, а не повірив першому кадру.
- **Чому агент так зробив (гіпотеза):** інструмент скріншота віддав попередній кадр (або вкладку до перезавантаження стилів). Агент майже оголосив «готово» за картинкою, хоча пункт 3 якраз учив не покладатись лише на неї.

## 3. Зміна користувача лишала вкладку «Архів»

- **Що просив:** Task A пункт 3 — пройти стани в браузері, зокрема перемикання Оля → Тарас.
- **Що видав:** `userSelect.addEventListener("change", load)` у `app/public/app.js` перечитував нотатки, але **не скидав** `filter`. Після вкладки «Архів» у Олі перемикання на Тараса лишало `aria-selected` на архіві: лічильники ставали «Активні (1) / Архів (0)», на екрані — порожній стан архіву, хоча в Тараса є активна нотатка.
- **Як помітив:** браузер під час пункту 3. `browser_select_option` змінив value на «Тарас», а список лишився порожнім, доки вручну не натиснули «Активні (1)».
- **Як полагодив:** під час Task D обробник `change` скидає `filter = "active"` і тоді викликає `load()`.
- **Чому агент так зробив (гіпотеза):** фільтр тримали окремо від `load()`, щоб кліки по вкладках не ходили на сервер. Зміну користувача звели до «просто перечитай список» і не запитали, яка вкладка має бути видима для нового caller.

## 4. `parsePositiveInt` лише на архіві, не на читанні/видаленні

- **Що просив:** Task B пункт 3 — валідувати архівний ендпоінт на сервері; Task C2 — полагодити `GET /api/notes/:id`.
- **Що видав:** для `PATCH .../archive` id має бути `/^[1-9]\d*$/`, інакше 400. `GET /api/notes/:id` і `DELETE /api/notes/:id` лишились на `Number(req.params.id)` (NaN / `3e2` тощо йдуть у SQL).
- **Як помітив:** рев’ю `app/src/app.js` під час Task D: `parsePositiveInt` оголошено нагорі, використовується один раз.
- **Як полагодив:** не уніфікував навмисно — засіяні тести й C2 вимагали фіксу власника в `WHERE`, не перепису всієї валідації id. Залишок зафіксовано тут.
- **Чому агент так зробив (гіпотеза):** валідацію робили в скоупі «пункт 3 Task B = тіло `archived` + id архіву». Інші маршрути не входили в формулювання промпта.

## Що агент зробив ДОБРЕ там, де я чекав проблем

- **Власник у SQL з першого дня архіву.** `UPDATE ... WHERE id = ? AND user_id = ?`, без «спочатку SELECT, потім if». C1 не потребував окремого фіксу — лише перевірки. Тест `will not archive someone else's note` це тримає.
- **Не закрив засіяну діру під час Task B.** `GET /api/notes/:id` лишився з `WHERE id = ?` і `user_id` у відповіді, доки не дійшли до C2. Інакше 9 засіяних тестів усе одно були б зелені, а воркшопний витік зник би «між ділом».
- **Тест C2 червонів до правки.** `will not read someone else's note` спочатку: `expected 404, got 200`. Відтворення: Оля на `/api/notes/3` отримувала `200` і `"пароль від сейфа: 1234"`. Потім `AND user_id = ?` — 19 тестів зелені.
- **Відповідь архіву вузька.** `{ id, archived }`, не весь рядок. Рядок `"true"` і число `1` — 400, стан у базі не змінюється (не `Boolean(archived)`).
- **Не вигадав зайвої колонки** на кшталт `is_deleted`. Одна `archived INTEGER NOT NULL DEFAULT 0` плюс `ALTER TABLE` для вже існуючого `notes.db`.

## Що я перевіряв і воно виявилось чистим

- `GET /api/notes` віддає лише нотатки caller (`user_id` у SELECT як умова, не в JSON).
- `DELETE` чужої нотатки — 404, рядок Тараса лишається (засіяний тест, зелений і до C2).
- `PATCH` чужої — 404, `archived` у Тараса лишається `false`.
- Після C2 `GET /api/notes/3` від Олі — 404 `{ error: "not found" }`, без `body` і без `user_id`.
- Сіди Оля/Тарас і три стартові нотатки після міграції на місці; `npm test` — 19/19.
- Кнопки архіву — справжні `<button type="button">` з текстом, висота 44 px; інпути форми мають видимі `<label>` (дерево доступності: `name: Заголовок`, `name: Текст`).
- У відповіді `PATCH` лише ключі `id` і `archived` (тест `toEqual` + `Object.keys`).
